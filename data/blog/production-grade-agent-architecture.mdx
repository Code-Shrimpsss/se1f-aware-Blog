一个大模型接上聊天框，很快就能做出“像 Agent”的演示：它理解问题、列出计划，甚至能生成一段看似正确的操作结果。但当系统真正进入业务流程，问题会突然变得具体：检索结果过期怎么办？工具执行到一半超时怎么办？重复请求会不会创建两张工单？模型为什么选择了这个动作？什么时候必须让人接管？

这些问题的答案不在一条更长的 Prompt 里。

生产级 Agent 的本质，是一套以模型为推理部件、以确定性工程为安全边界的执行系统。模型负责处理模糊性，系统负责约束风险、保存状态、提供证据，并让每一步都可以恢复和解释。

## 聊天机器人不是 Agent 系统

聊天机器人通常止于“生成答案”，Agent 则需要“改变外部状态”。后者一旦调用搜索、数据库、工单、支付或部署工具，就进入了传统分布式系统长期面对的领域：权限、并发、幂等、重试、审计和故障恢复。

可以用一个简单公式描述两者的差别：

> Agent 交付能力 = 模型能力 × 上下文质量 × 工具可靠性 × 状态一致性 × 可观测性

这里用乘法而不是加法，是因为任何一层接近零，整体就会失效。一个推理能力很强的模型，如果拿到错误的客户资料，仍会稳定地产生错误决策；一个工具定义很漂亮的系统，如果没有幂等保护，也可能把一次重试变成两次扣款。

## 第一层：上下文与检索

Agent 首先需要回答的不是“我知道什么”，而是“完成这次任务，哪些信息是可信且必要的”。上下文层的职责，是把分散的信息整理为带来源、时效和权限边界的证据集合。

典型流程包括：

1. 识别用户意图、实体与时间范围。
2. 根据用户身份过滤可访问的数据域。
3. 混合使用关键词检索、向量检索和结构化查询。
4. 对结果重排、去重，并保留来源和更新时间。
5. 在送入模型前控制上下文预算。

RAG 最常见的问题不是“没搜到”，而是“搜到了看起来相似、实际已经过期的内容”。因此每个上下文片段至少应携带 `source`、`updatedAt`、`owner` 和 `confidence`。对于价格、库存、权限等高变化数据，向量库只能帮助定位，最终事实应回到权威 API 或数据库确认。

一个实用原则是：**检索负责召回候选，业务系统负责确认事实。**

## 第二层：推理与任务分解

推理层把用户目标转换为可执行步骤。这里不应该只依赖一段不可见的自由推理，而应让模型输出受约束的计划结构，例如：目标、前置条件、步骤、预期结果与停止条件。

对于短任务，一次模型调用就足够；对于长任务，更可靠的做法是循环执行“小步计划”：

1. 根据当前状态选择下一步，而不是一次生成全部动作。
2. 执行一个工具调用。
3. 将结构化结果写回状态。
4. 检查目标是否完成、是否需要改道或人工介入。

这种模式把错误限制在单个步骤内，也避免早期计划在环境变化后继续盲目执行。系统还应设置最大步骤数、预算和截止时间，防止 Agent 在无法完成的任务上无限循环。

重要的是，模型可以提出计划，但权限判断、预算限制和危险动作审批必须由确定性代码完成。不要让模型自己决定自己是否有权执行。

## 第三层：工具契约与执行边界

工具是 Agent 与现实世界的接口。一个生产工具不应只是“函数名加一句描述”，而应是一份明确契约：输入约束、输出结构、权限要求、超时、重试策略和副作用等级。

下面是一个最小化的 TypeScript 工具契约：

```ts
type ToolContext = {
  userId: string
  runId: string
  idempotencyKey: string
  signal: AbortSignal
}

type ToolResult<T> =
  | { ok: true; data: T; evidence?: string[] }
  | { ok: false; code: string; retryable: boolean; message: string }

interface AgentTool<Input, Output> {
  name: string
  risk: 'read' | 'write' | 'irreversible'
  validate(input: unknown): Input
  authorize(input: Input, context: ToolContext): Promise<boolean>
  execute(input: Input, context: ToolContext): Promise<ToolResult<Output>>
}
```

这份契约刻意把 `validate`、`authorize` 和 `execute` 分开。模型生成的参数永远是不可信输入；即使参数格式正确，也不意味着当前用户有权执行。对于发邮件、删除数据、付款等副作用操作，还应加入预览与确认阶段。

工具返回值也不应是一段随意文本。稳定的错误码和 `retryable` 标记，能让编排器区分“网络抖动可以重试”和“权限不足必须停止”。

## 第四层：状态、记忆与故障恢复

只把对话消息存在数组里，并不能构成可靠状态。生产任务至少要区分三类数据：

- **会话状态**：当前目标、已完成步骤、待确认动作。
- **业务状态**：订单、工单、部署等权威系统中的真实结果。
- **长期记忆**：经用户授权后保存的稳定偏好与历史事实。

每次运行都应有唯一 `runId`，每个有副作用的动作都应携带幂等键。状态机记录动作的 `planned → approved → running → succeeded/failed` 变化，使进程崩溃后能够从最后一个确定节点继续，而不是让模型凭聊天记录猜测发生了什么。

重试同样需要边界：读操作通常可以指数退避重试；写操作只有在工具提供幂等保证时才能自动重试；不可逆操作则应优先进入人工确认。长期记忆不能把模型总结当作事实直接写入，至少要保留来源、置信度和可删除机制。

## 第五层：可观测性、评估与人工介入

普通服务记录请求与响应，Agent 还需要记录“为什么走到这里”。一条完整运行轨迹应串联：用户目标、上下文来源、模型与版本、计划变更、工具参数摘要、权限结果、耗时、Token 成本和最终状态。

可观测性不是为了收集更多日志，而是为了回答三个问题：

1. 失败发生在哪一层？
2. 同样输入能否复现？
3. 是模型问题、数据问题，还是系统策略问题？

评估也不能只看最终文本是否流畅。更有价值的指标包括任务完成率、错误工具调用率、无依据断言率、平均人工接管次数、恢复成功率和单位成功任务成本。离线评测用于比较版本，线上抽样与真实反馈用于发现分布外问题。

人工介入不是失败兜底，而是架构中的正常节点。低置信度、权限冲突、高金额操作、隐私数据访问和连续失败，都应触发清晰的接管流程，并把当前证据、已执行步骤和建议动作一起交给人，而不是只显示“发生错误”。

## 一次请求如何穿过五层

以“根据客户最近的反馈创建一张高优先级工单”为例：

```text
用户目标
   ↓
身份与权限 ── 不允许 ──→ 结束并解释
   ↓
上下文层：检索客户、反馈与服务等级，附上来源
   ↓
推理层：判断是否满足高优先级规则，生成待执行计划
   ↓
人工确认（当规则边界模糊或涉及敏感客户）
   ↓
工具层：校验参数，以幂等键创建工单
   ↓
状态层：保存工单 ID、结果与下一步
   ↓
可观测层：记录证据、决策、耗时与成本
   ↓
向用户返回结果，以及可以核验的链接
```

这条链路中，模型可以提取反馈主题并建议优先级，但客户权限、高优先级硬规则和工单是否真的创建成功，都由外部系统确认。

## 常见失败模式

| 失败模式 | 表面现象 | 工程对策 |
| --- | --- | --- |
| 上下文污染 | 回答引用了其他客户数据 | 检索前做租户与权限过滤，结果携带来源 |
| 计划漂移 | 执行中逐渐偏离原目标 | 每步对照目标与停止条件，限制最大步数 |
| 工具幻觉 | 调用不存在的参数或动作 | Schema 校验，工具白名单，结构化错误 |
| 重复副作用 | 超时重试创建两张工单 | 幂等键、状态机、写操作重试策略 |
| 静默失败 | Agent 声称完成但外部状态未改变 | 读取权威系统回验，返回可核验 ID |
| 无限循环 | 多个工具之间来回尝试 | 步数、时间和成本预算，失败阈值后接管 |
| 无法复现 | 同类问题偶发且原因不明 | 保存模型版本、上下文快照与完整运行轨迹 |

## 上线前检查清单

在把 Agent 接入真实业务前，我会至少确认以下事项：

- 每个工具都有输入 Schema、权限校验和结构化错误。
- 所有写操作都有明确副作用等级与幂等策略。
- 高风险动作支持预览、确认和撤销，或明确说明不可撤销。
- 检索结果保留来源、更新时间与访问边界。
- 任务有步数、时长、Token 和费用预算。
- 运行状态可以持久化，并能在中断后安全恢复。
- 每次最终结论都能关联证据或权威系统结果。
- 低置信度与连续失败有人工接管路径。
- 离线评测覆盖正常、边界、对抗与工具故障场景。
- 线上有分层指标、抽样审查和版本回滚能力。
- 用户可以知道 Agent 做了什么，也能删除被保存的长期记忆。

## 可靠性本身就是产品

Agent 最有价值的地方，不是把聊天界面做得更像人，而是把过去需要人在多个系统之间来回切换的流程，重组为可理解、可控制的交付体验。

模型能力会继续快速变化，今天需要复杂提示才能完成的任务，明天可能成为基础能力。但上下文边界、工具契约、状态一致性、可观测性和人工责任不会因此消失。它们决定一个系统是在演示中“偶尔惊艳”，还是在真实世界里“持续可信”。

当 Agent 开始改变外部状态时，可靠性就不再是后台工程细节——它本身就是用户正在使用的产品。
